## 一、值得借鉴的思想

- **不整理也应当成立**：未分类不意味着记录未完成；没有 tag、链接或精心标题的记录也应能保存和找回。
- **组织发生在查询时**：子流是持续有效的筛选条件，不是移动文档的容器；删除子流不应删除记录。
- **时间是低负担的基本坐标**：记录尚未被理解，也有发生的时间。时间邻近、明确引用和语义相似是三种不同的找回路径。
- **归档与注意力分开**：退出当前视野不等于删除或搬走；不应把所有历史记录同时压给用户。
- **信息在合适时机重新出现**：未来文档的启发在于把内容交给未来的自己，而非额外制造待办。实际创建时间与再次出现时间应区分。
- **沿用已有编辑工具**：Org 负责写作，Supertag 负责组织、关系与呈现，不必重造编辑系统。
- **性能也是交互承诺**：无摩擦记录不能被反复的全库处理打断；搜索覆盖范围与展示、格式化成本应分开考虑。

以上包含对论文的解释及对 Supertag 的延伸，不代表所有项目都要实现。

## 二、代码对照

### Stream

`supertag-view-stream.el`：

- `supertag-view-stream--created-time` 读取 `:created-at`。
- `supertag-view-stream--node-before-p` 按创建时间排序。
- `supertag-view-stream--build-state` 要求 tag，通过 `supertag-view-api-nodes-by-tag` 取得节点。

因此当前已有标签范围内的时间流，但不是由任意查询生成的通用子流。查询引擎与 Stream 还没有完全统一。

### 查询及数据接口

- `supertag-query.el` 已有排序、分组与聚合处理。
- `supertag-api-query` 返回节点结果或聚合结果，并能标示节点结果是否因 limit 截断。
- `supertag-api-node` 返回 ID、标题、正文、文件、hash、标签、属性、命名关系、出链和反链。

总结材料可以直接从 Store 读取，不需要为了收集正文逐个打开目标文件。边界是：Store 是同步后的投影，未保存或尚未同步的编辑可能不在其中。第一版可明确只总结已同步内容，不应悄悄替用户保存所有文件。

### 当前 AI 功能

`supertag-ai.el` 的 `supertag-ai--start` 当前围绕单节点属性提取：通过 Org 节点上下文读取标题、属性与正文，再经 `superchat-runtime-submit` 异步请求模型，使用 `:tools 'none`。

已有请求、取消、失败处理及候选确认的基础。批量属性提取仍是逐节点处理，不是跨节点综合理解。可借鉴请求机制与人工确认原则，但不应把集合总结硬塞进属性候选结构。

## 三、RAG 历史核对

用户记得 Supertag 曾复用 Chai 的 RAG 方法。

已确认：历史提交 `4d9967b` 存在 `supertag-rag.el`，使用 `llm.el`，流程为：

自然语言问题 → LLM 生成查询表达式 → 查询 Store → 提取正文和元信息 → LLM 生成回答。

相关函数：

- `supertag-rag--generate-sexp-from-question`
- `supertag-rag--retrieve-context-from-ids`
- `supertag-rag--generate-answer`

当前主目录已无这个文件。未找到直接引用 Chai 的证据，不能确认是直接复用还是思路借鉴；这个来源问题保持未决。

当前 `supertag-semantic.el` 是节点 embedding、相似度排序及 Similar 呈现，有独立向量索引，但没有接上基于检索结果的生成回答，不是完整 RAG。

区分两种用途：

- **全库问答**：先检索与问题相关的材料，可沿用 RAG 路线。
- **指定集合 summarize**：需要交代整个范围，不应仅取最相似的几条，否则容易漏掉反例和少数观点。

## 四、用户对 Summarize 的关键纠正

用户指出：Lifestreams 的 summarize 可以图形化呈现，而这正是 LLM 可以帮助的地方。

因此功能不应被收窄为“生成一篇文字摘要”。更准确的目标是：

> 把一组记录转换成适合整体理解的表示。

例子：

| 问题 | 可能的表示 |
|---|---|
| 项目如何发展到今天 | 时间线 |
| 什么仍未解决 | 状态表、问题清单 |
| 各种方案有何区别 | 对比矩阵 |
| 哪些观点支持或反对结论 | 证据关系图 |
| 注意力分布在哪里 | 有可靠统计依据的分布图 |

这些是候选设计，不是已实现能力，也不全是论文中的具体例子。

LLM 的主要价值是从自由文本中辨认出值得呈现的结构，使用户无需在记录时提前填写大量结构化字段。

## 五、提出的最小实现方向（尚未批准实施）

```text
用户选定 Stream / 一组节点，并提出问题
  → Store 提供正文与来源
  → LLM 提取事件、观点、状态及关系
  → Supertag 用固定组件呈现表格、时间线等
  → 点击呈现条目回到原始节点
  → 用户决定是否保存为新笔记
```

建议先做带节点链接的对比表或时间线，而非完整图谱或自主整理 agent。

模型生成结构化呈现数据，不直接执行任意模型生成的界面代码。可计算的数量、排序和求和由代码完成；主题划分、归纳及因果推断须区分事实与模型解释。

关键边界：

1. 明确材料范围、遗漏和截断；部分材料不能冒充全库。
2. 重要判断附来源链接；ID 校验只能验证来源范围，不能保证语义正确。
3. 默认只生成草稿，不移动、删除、改写原始笔记。
4. 保存的总结与实时概览分开，历史总结不应无声覆盖。
5. 避免生成总结默认再混入下一轮材料，形成模型总结自身的循环。
6. 远程模型的材料发送范围和接收方应明确。

## 六、当前共识与未决项

- 用户认可借助 AI 实现 summarize 的方向，强调应包含图形化、结构化的理解呈现。
- 更适合将它称为“理解视图”：Stream 展示记录，Summarize 帮助观察记录集合意味着什么。
- 不需要先实现通用子流，也不需要先拥有自主修改知识库的 agent。
- 首版交互、具体视图、模型输入限制、保存格式及刷新规则尚未确定。
- Chai 与旧 RAG 实现的确切渊源尚未证实。
